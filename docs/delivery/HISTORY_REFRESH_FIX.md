# Streamlit 刷新后历史会话恢复（2026-10-30）

用户确认故障发生在旧版 `http://127.0.0.1:8510`，不是18520的React页面。

## 原因与修复

旧版将导航目录和当前任务编号仅保存在 `st.session_state`。浏览器刷新建立新Streamlit会话后，这些字段消失；数据库中的LangGraph检查点仍在，但界面不能自动发现它们。

- 增加认证后的只读 `GET /conversations`。从已有MySQL/SQLite检查点读取当前客户最近100条会话，不新建表、不迁移或清空旧数据。
- 登录后从服务器重建历史列表；URL仅保存非敏感会话编号 `conversation`，刷新重新登录后恢复原会话，没有编号时选最近会话。
- 提供刷新历史列表、新建对话和手动加载旧任务。退出登录或切换API时清除选中编号；读取任务仍走原有身份和归属校验。
- 密码和登录令牌不写入URL。Streamlit刷新仍可能要求重新登录；本修复恢复对话，不通过长期存储令牌改变登录安全边界。

适配器针对锁定的checkpoint-mysql 3.0.0和SQLite保存器：只查询根图会话，精确二进制匹配客户前缀并校验任务编号，不反序列化其他客户的检查点。MySQL使用保存器管理的连接/锁，SQLite使用保存器锁。后续升级保存器版本须运行回归。

## 实际验证

- 修复前新增回归3项均失败；修复后3项通过，覆盖后端重启持久化、精确客户隔离、只读客户端及全新Streamlit会话恢复。
- `pytest tests/delivery tests/platform -q`：153通过，10个现有依赖警告。
- 回移到用户实际运行的旧版后，`pytest tests/delivery -q`：86通过，6个现有依赖警告。
- 真实Edge + Streamlit + MySQL：输入一次只读测试问题、刷新/重新登录、恢复较早会话、切换客户，最终浏览器验收1项通过。恢复前后消息及模型调用计数相同，没有重发原请求。
- 首次浏览器脚本过早读取了仅有人类消息的初始检查点，导致模型计数断言失败；保留该记录，改为等待持久化最终回复。该次已发送问题后，最终验收复用同一会话，不再追加模型调用。

原始记录在 `evaluation/history-refresh/20261030/`。一次真实测试问题只涉及对话检查点，不创建退款/补发或业务工单。React前端代码和旧实验结果未修改。
