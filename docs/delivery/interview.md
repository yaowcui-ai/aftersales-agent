# 项目面试问答与贡献说明

回答以实际代码和本人能够解释、演示的部分为准。项目没有对外上线交易规模、招聘指标或算法创新结论；实际测试与模型评测结果另见交付验证记录及 [evaluation.md](evaluation.md)。

## 1. 用一分钟介绍这个项目？

这是基于 LangGraph、MCP、FastAPI、Streamlit 和 MySQL 的电商售后演示项目。客户提出物流、退款或补发需求，单 Agent 查询订单事实并生成候选动作，审批员确认后由受控 Python 事务执行，再保存工单与回复。退款和补发是模拟业务，展示重点是身份隔离、人工审批与失败后恢复。[架构图](architecture.md) 展示完整边界。

## 2. 哪些来自开源框架，哪些是本项目增加的？

基础来自 Joshua Carroll 的 `agent-service-toolkit`，MIT 许可，基线提交 `58f6a059f9787db1a68946030b35dd61023662fa`，保留 [LICENSE](../../LICENSE)。复用模型工厂、LangGraph 依赖和已有 MySQL checkpoint 组件；本项目新增售后规则与表、不可变审批、身份隔离、MCP 工具、专用 API/UI、故障回归和部署。不能把上游已有 FastAPI、通用 UI 或模型适配能力全部称为个人原创，来源见 [framework-baseline.md](../framework-baseline.md)。

## 3. 你本人具体做了什么，AI 做了什么？

我参与了需求与边界确认，并亲手实践过最小状态图、MySQL checkpoint 保存读取、`interrupt/Command` 暂停恢复和工具封装等代表性机制；过程有 [environment-check.md](../environment-check.md) 记录。后续我明确授权助手完成剩余批量实现、测试和交付整理。因此我会说明哪些代码是助手实现，并用实际代码讲清原理、验证和限制，不声称全部由本人独立手写。尚未掌握的部分应继续复盘，不用“独立开发”替代理解。

## 4. DeepSeek 是怎样查询 MySQL 的？

模型通过 `Runtime.model → get_bound_model → get_model` 得到工具定义并返回 `tool_calls`。随后图的 `tools_node` 调 MCP，MCP Python 函数调用 `Store`，SQLAlchemy/asyncmy 执行参数化 SQL，再把结果交回模型。DeepSeek 没有数据库密码，也不直接执行 SQL。最终 `Runtime.reply` 会再次调用模型表达已提交结果，具体位置见 [代码导读](learning-guide.md)。

## 5. 为什么用单 Agent，为什么没有 RAG 或多 Agent？

本场景事实源是结构化订单、包裹、库存和工单，查询工具已经能获取所需信息。一个模型节点配合显式图状态、工具、审批和执行节点即可完成流程。目前没有必须检索长文档的需求，也没有需要多角色自主协作的业务任务，因此不额外引入 RAG 或多 Agent。这里的价值是可靠地控制业务流程，不以 Agent 数量或模型创新作为卖点。

## 6. 人工审批怎样防止被提示词绕过？

模型只能提出 `prepare_action`；`Store.prepare` 持久化不可变候选。审批接口从登录 token 识别审批员，校验 `action_id + version`，并保存决定。恢复时图读取数据库批准记录，MCP 执行上下文还绑定客户与动作；用户聊天声称“已批准”不能替代这些检查。拒绝没有业务副作用，审批请求夹带新金额会被接口拒绝。

## 7. 怎样防止越权查询和客户冒充审批员？

登录 token 带签名、到期时间、角色和服务端客户绑定；API 还与当前账户配置核对。模型查询参数不开放客户身份，MCP 从短时签名上下文取得客户。普通网页登录 token 与 MCP token 的用途不同，不能互换；执行 token 还限定单个动作。客户只能读取本人订单、工单和任务，审批员才有决定及工单状态处理权限，代码见 [security.py](../../src/aftersales_delivery/security.py) 和 [api.py](../../src/aftersales_delivery/api.py)。

## 8. 有 checkpoint 为什么还需要幂等？

checkpoint 保存图位置，不能保证外部业务与节点状态同时提交。可能退款事务成功但响应丢失，恢复时节点重新执行。业务层以固定动作编号、唯一约束和已保存结果防重；已完成动作直接返回原结果。图先查询动作是否完成，也减少重复调用，但最终不变量由业务数据库保证。[business.py](../../src/aftersales_delivery/business.py) 中 `execute` 是主要入口。

## 9. 退款和库存并发时怎样保证正确？

MySQL 事务锁定动作、订单及必要库存，执行时重新检查业务条件，并用带余额或库存条件的更新守住下限与退款上限。金额存整数分，避免浮点累计误差；流水对动作有唯一约束。SQLite 测试采用立即写事务，但数据库锁行为不同，因此需要单独观察真实 MySQL 并发结果。当前没有真实支付调用，接支付渠道还需要外部交易幂等、对账和异常补偿。

## 10. 退款成功但模型回复失败怎么办？

业务动作保持 `completed`，工单和退款流水已经保存；图可显示 `reply_failed`，接口返回“业务完成、回复失败”。审批员重试同一动作后，`Runtime.resume` 重新安排回复节点；业务层不会再次退款。回归 [test_recovery.py](../../tests/delivery/test_recovery.py) 通过真实 SQLite 业务与 checkpoint 核对流水、事件和工单数量，也覆盖应用重启后的待审批恢复。

## 11. 教学 MVP 到交付版改变了什么，为什么保留旧项目？

原教学 MVP 用逐步练习验证状态、工具、审批和幂等，MCP 学习路径包含 stdio。交付版新增 `aftersales_delivery` 应用与 Streamable HTTP MCP，让 API 与工具服务独立运行，并加入客户/审批员 UI、恢复接口和部署。它复用本机 MySQL 服务与既有 checkpoint 组件，业务数据进入新的 `aftersales_delivery` 库；保留旧入口、旧库与原服务便于对照和保护已有系统。新端口是 UI 8510、API 8090、MCP 8091，不能把同一个 MySQL 服务误说成同一业务库。

## 12. 怎样评价效果，离生产还有什么距离？

先用确定性测试验证权限、规则、并发和故障恢复，再用固定开发/保留案例评估真实模型的理解、工具选择及结果；调用次数、Token 和耗时依据实际记录，未运行或缺失部分如实保留。当前没有可据此宣称的线上业务提升或完整计费结论。部署按单 API worker 验证，尚无企业 SSO、公网 HTTPS 网关、多实例 checkpoint 调度或真实支付/仓储；签名 token 和本机演示账户不能直接代表生产账户体系。审计用自增 `sequence` 保留事件插入顺序，便于追查审批与执行，但仍需补充真实生产监控和外部对账。


## 最新公开复测口径

2026-10-21固定48案例各3次的完整真实模型回归复测为 **140/144（97.2%）**，4条失败全部保留；80项应用离线测试及7步聊天浏览器验证通过。此处是查看历史案例后的回归复测，不是未见独立测试；历史129/144记录保留，不回填。模型调用的有限重试属于端到端执行流程，144是任务数。详细条件、失败原因及原始记录见[评测方法](evaluation.md#2026年10月21日公开发布复测)与[验收记录](acceptance.md)。
