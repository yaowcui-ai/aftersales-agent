## 缺陷、边界和优先级

1. P0：没有退货、售后时限、风险阈值等可执行规则；原 demo 对 shipped 也允许直接退款，不能套用新业务承诺。升级采用附加策略表，只对有策略的沙箱订单启用新规则，旧记录原样保留。
2. P0：审批未单独记录原因、时间、冻结快照摘要；需要持久化审批对象、版本与参数摘要，并在执行前再次比对；取消/审批/执行竞态须行锁串行。
3. P0：业务失败和任务失败可分离，客户端可能只见503；需要明确业务状态、可恢复回复和持久化任务索引，禁止“HTTP成功即业务成功”。
4. P1：用户和管理员没有 React 界面；缺少直接订单/物流 REST、表单申请、审核理由、审计聚合、失败任务和统计接口。
5. P1：只有配置账户，没有产品用户资料表；保留认证兼容层并同步非敏感用户资料，禁止复制密码进入日志。
6. P1：旧80/83项主要替身模型+SQLite。旧 MySQL、MCP、Docker、浏览器证据保留，但不能替代新规则/React/故障注入验证。
7. P1：48案例含重复及已见 heldout，新增120个条件明确的独立场景，冻结开发/验证/测试分区，不调预期凑分。
8. P1：缺乏公平 B0/B1/B2/B3 实际执行；弱基线只能隔离运行。要报告模型、调用次数、参数、数据库效果与不可比项。
9. P2：单 API worker 的内存锁不支持跨实例全局互斥；最终业务正确性依赖数据库锁/唯一约束。保持单worker演示，不宣称生产集群能力。
10. P2：无企业SSO、真实支付/仓储、真实客户试验。全程标注本地沙箱，不报告企业降本收益。

## 复用与升级顺序

复用模型工厂、图/检查点、MCP认证传输、Store事务和旧表。先补业务/审批确定性边界，再接 REST 和 React，随后运行隔离故障/安全/MySQL及真实浏览器闭环，最后冻结实验输入、有限真实模型与对照、整理证据。用户明确授权持续实施，审计不是停止点。

上述P0/P1已通过新增规则、冻结审计、React与REST、任务索引/恢复和分层评测落实。额外发现并修复收货/取消提交后的检查点双写窗口、退货授权恢复白名单、request/thread混用、MCP嵌套异常及浏览器刷新定位。最终Python150项、前端6项通过；MySQL/MCP7项、真实进程恢复1次、React真实Agent闭环均有独立记录。
