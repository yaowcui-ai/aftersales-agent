# 售后业务与 Agent 工作流

## 自然语言入口

1. 服务端从登录令牌取身份，建立客户隔离的thread。
2. 模型选择 `list_orders/get_order/get_shipments/get_inventory/get_case` 查询事实；缺少具体订单时补问。“有几个订单”直接调用列表工具。
3. 明确诉求后模型只能提出 `prepare_action`，Store确定性检验状态、期限、金额、数量、归属和库存。
4. 事务内创建动作和ticket，图用interrupt暂停；此时没有退款或库存扣减。
5. 审批员通过真实HTTP界面提交决定及理由，服务端保存对象/版本/冻结快照摘要。
6. 恢复图后读取真实审批，独立MCP调用执行；执行前再检验规则和冻结对象。
7. 核对已保存账本结果，回复用户；回复失败仅恢复结果表达，不重复业务。

表单入口 `/requests` 与自然语言共用Store、审批和图状态，但没有模型理解阶段。request_id是客户端稳定申请标识，真实thread为服务端映射；成功后保存返回thread，丢响应时调用 `/requests/{request_id}`。不能混用request_id/action_id/thread_id。

## 规则与状态

| 诉求 | 前置条件 | 审批后变化 | 禁止动作 |
|---|---|---|---|
| 未发货退款 | paid、窗口内、余额足够 | 一次模拟退款，累计已退增加，case resolved | 未审批退款、超额退款 |
| 退货退款 | shipped/delivered、窗口内、余额足够 | 先awaiting_return，收货前已退不变；审批员收货后才退款一次 | 直接将授权当作已退款 |
| 补发/错漏发 | shipped/delivered、有剩余数量和库存、未全退 | 一次补发记录，库存/可补数量同时扣减 | paid补发、超卖、重复扣减 |
| 物流异常/丢件申请 | 当前客户订单 | 建open工单，等待处理 | 把空物流推断成丢件或已解决 |
| 超期/取消/异常金额 | 不符合确定性政策 | 明确错误码，无业务效果 | 模型自行扩大权限 |
| 高风险/高额 | 策略标记manual_review | 显示人工复核；仍须真实审批 | 自动批准 |
| 撤销申请 | 待批/已批未完成/待收货，锁内检验 | cancelled，不能继续执行 | 撤销已完成退款并抹除账本 |

审批与执行之间订单状态、余额、库存或期限发生变化时，再校验并持久化失败。已批准退货的收货不因运输跨过申请窗口而自动失效，但仍检验原批准对象、余额和订单状态。

## 故障恢复

客户使用“读取已保存状态”，审批员使用“恢复原动作”；不在超时后生成新申请。取消和收货都需要处理“数据库已提交、图尚未保存”的双写窗口。产品API给出 `business_status` 和恢复提示；快照只负责继续执行，账本负责最终业务事实。

## 模型边界

当前为单Agent。查询工具观察、物流描述及用户文本均是不可信数据；工具白名单、客户隔离、审批及金额/库存限制由程序执行。提示词只是行为指导，不能替代服务器授权。Token和耗时记录来自真实返回，缺失不补零。
